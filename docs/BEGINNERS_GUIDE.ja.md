## 1. そもそも画面はどうやって光っているのか

PC のグラフィックスとの一番大きな違いは、**MCU 側に「画面そのもの」が無い**ことです。

M5Stack や ESP32 につながっている小型 LCD は、たいてい ILI9341 / ST7789 のような
**コントローラ内蔵パネル**です。パネルの中に画素ぶんのメモリ（GRAM）があり、
表示回路はそこを一定周期で読み出して液晶に出し続けています。MCU がやるのは、

> SPI（または I80 パラレル）で **「この矩形領域に、この画素列を書き込め」** と送りつけること

だけです。送った瞬間にパネル側の GRAM が書き換わり、次のリフレッシュで見えます。

```
  ESP32                            LCD パネル
  ┌────────────────┐  SPI 40〜80MHz  ┌──────────────────┐
  │ あなたのコード  │ ──────────────► │ コントローラ      │
  │ lcd.fillRect() │  「x,y,w,h に   │   ↓ 書き込み      │
  └────────────────┘   このピクセル」 │ GRAM（画素メモリ）│
                                      │   ↓ 常時読み出し  │
                                      │ 液晶パネル        │
                                      └──────────────────┘
```

ここから、組み込み描画の性質がほぼ全部導けます。

- **描いた端から見える。** `fillScreen()` して `drawString()` すると、
  「真っ黒になった画面」と「文字が出た画面」の**両方**が順に表示されます。
  PC のようにフレーム単位で切り替わってはくれません。
- **転送量＝時間。** 320×240 の 16bit 全画面は 320 × 240 × 2 = **153,600 バイト**。
  SPI 40MHz なら約 **32 ms**、80MHz でも約 15 ms かかります。
  つまり**全画面を描き直す限り、Core2 では物理的に約 31fps が上限**です。
  これは描画の工夫ではどうにもならない床です。
- **読み戻しは基本できない（遅い）。** 多くの構成でパネルからの読み出しは
  未サポートか非常に低速です。「今の画面の上に半透明で重ねる」が難しいのはこのためです。

### 色は RGB565

送るのは 1 画素 16 ビット、赤 5 / 緑 6 / 青 5 ビットです。
`#4CAF50` のような 24bit 色は必ずこの粒度に丸められます。
グラデーションで縞（バンディング）が出るのはそのせいで、バグではありません。

## 2. なぜちらつくのか

「描いた端から見える」ことの直接の帰結です。よくある更新ループを書くと：

```cpp
void loop() {
  lcd.fillScreen(TFT_BLACK);          // ← ここで画面が真っ黒になる（見える！）
  lcd.drawString("Temp", 10, 10);     // ← 文字が戻ってくる
  lcd.drawString("24.5C", 10, 40);
  delay(100);
}
```

人間の目には、1 秒に 10 回の**黒い瞬き**として見えます。これがちらつきの正体です。
「消してから描く」の**消してから**が見えてしまっている。

素朴な回避策は 2 つありますが、どちらも壁にぶつかります。

**(a) 消さずに、変わった部分だけ上書きする。**
数値が `100` → `99` と短くなると前の桁が残ります。背景を塗ってから書けば、
今度はその小さな矩形だけがちらつきます。パーツが増えるほど
「どこを消すか」の管理が破綻していきます。

**(b) 変化したときだけ描く。**
ちらつく回数は減りますが、1 回ぶんのちらつきは残ります。
アニメーションやリアルタイム値には使えません。

根本の問題は、**画面の更新が原子的でない**ことです。中間状態が見えてしまう。
ならば、中間状態を**見えない場所で**作ればいい。

## 3. ダブルバッファ — と、それが載らない現実

答えははっきりしています。**RAM 上に画面と同じ大きさのバッファを持ち、そこに描き、
完成してから一気にパネルへ転送する。** これがダブルバッファです。
パネルが見るのは完成品だけなので、中間状態は原理的に見えません。

問題は値段です。

| 画面 | 全画面バッファ（16bit） |
| --- | --- |
| 128×128（AtomS3） | 32 KB |
| 135×240（StickC Plus） | 63 KB |
| 240×135（Cardputer） | 63 KB |
| **320×240（Core / Core2）** | **150 KB** |
| 320×480（CoreS3 縦） | 300 KB |
| 720×1280（Tab5） | 1.8 MB |

一方、ESP32 の内蔵 DRAM は約 320 KB、そこから WiFi/BLE スタック・ヒープの断片化・
自分のバッファが引かれます。しかも問題は**総量ではなく連続領域**です。

> **実測（Core2、`bench/`）**：空きヒープが **310 KB** ある状態でも、
> 320×240 の全画面スプライト（150 KB の**連続**確保）は**失敗しました**。
> ベンチのログに `full sprite alloc failed (skipped)` と残っています。

つまり「計算上は入るはず」でも入りません。これが組み込み GUI の中心的なジレンマです。
**ちらつきを消すにはバッファが要る。バッファを置く連続 RAM が無い。**

PSRAM 搭載機なら容量は足ります。ただし PSRAM は遅く、しかも
**LovyanGFX は PSRAM 上のスプライトを DMA 無しで push します**。同じ Core2 での実測：

| 方式 | 描画 | 転送 | 1 フレーム | fps |
| --- | --- | --- | --- | --- |
| PSRAM 全画面スプライト | 13.8 ms | 32.0 ms | **45.8 ms** | 21.8 |
| タイル分割（本ライブラリ、内蔵 RAM 38 KB） | — | — | **31.0 ms** | **32.3** |

**150 KB 使ったほうが、38 KB より遅い。** これがこのライブラリの存在理由です。

## 4. タイル分割という妥協

妥協点は「全画面バッファを持たず、**画面を横帯（タイル）に切って、1 本ずつ完成させて送る**」です。

```
   画面（仮想）                  実 RAM 上のタイルバッファ
  ┌─────────────┐  タイル0       ┌─────────────┐
  │  タイル 0   │ ──描画──────►  │  ~19 KB × 2 │ ──DMA──► パネル
  ├─────────────┤  タイル1       └─────────────┘
  │  タイル 1   │ ──描画──────►      （使い回す）
  ├─────────────┤
  │     …       │
  └─────────────┘
```

320×240 なら 1 行 = 320 × 2 = 640 バイト。既定の予算 19,200 バイトでは
19200 / 640 = **30 行**が 1 タイル、つまり **8 タイル**に分割されます。
必要な RAM は 19 KB × 2 枚 = **約 38 KB**。150 KB の 1/4 で、しかも 1 回あたりの確保が
小さいので**断片化に強い**（3 章の「310 KB 空きでも失敗」が起きない）。

### あなたの描画関数は「全画面座標」のまま

タイル分割を自分で書くと、Y オフセットの計算がすべての描画呼び出しに混ざって破綻します。
LGFXVirtualCanvas は**描画関数を全画面座標で 1 つ書かせて、それをタイルごとに実行**します。
オフセットとクリッピングはライブラリ側が隠します。

```cpp
void drawScene(LGFXVirtualCanvas& g) {
  g.fillScreen(TFT_BLACK);
  g.fillCircle(160, 120, 40, TFT_YELLOW);   // ← 全画面座標のまま書ける
}
screen.render(drawScene);                    // ← 中で 8 回呼ばれる
```

**これが一番重要なクセです。** 描画関数は 1 フレームにつき**タイル数だけ実行されます**。
`fillCircle` はタイル外ではクリップで消えるだけなので絵は正しくなりますが、
**関数の中でやった計算やセンサ読み取りは 8 回走ります**（→ [9 章](#9-最重要の落とし穴コールバックはタイル数ぶん走る)）。

### ここで DMA が効いてくる

DMA（Direct Memory Access）は、**CPU を介さずにメモリ ↔ 周辺機器を転送する**ハードウェアです。
LovyanGFX は、内蔵 RAM 上のスプライトを `pushSprite` するとき **非同期 SPI-DMA** を起動し、
**転送の完了を待たずに戻ってきます**。CPU はすぐ次の仕事に移れる。

ここでタイルバッファが 2 枚ある意味が出ます。

```
  時間 ──────────────────────────────────────────►
  CPU:  描画 T0 │ 描画 T1 │ 描画 T2 │ 描画 T3 │ …
  DMA:          │ 転送 T0 │ 転送 T1 │ 転送 T2 │ …
                 ↑ 重なっている
```

タイル 0 を DMA が転送している間に、CPU はもう一方のバッファにタイル 1 を描く（ping-pong）。
結果、**1 フレームの時間 ≈ max(描画の合計, 転送の合計)** になります。
バッファが 1 枚だと、転送中のバッファを上書きすると絵が壊れるので毎回 `waitDMA()` が要り、
**描画 + 転送の足し算**になります。だから LGFXVirtualCanvas は
**2 タイル以上になる面では自動でダブルバッファを有効化**します
（1 タイルなら重ねる相手が無いので単一のまま。SPEC §10.5）。

## 5. 最初の 1 枚を出す

必要なのは 3 つだけです。**面を宣言する・描画関数を書く・render する。**

```cpp
#include <M5Unified.h>          // ← グラフィックスライブラリが先
#include <LGFXVirtualCanvas.h>  // ← その後

LGFXVirtualScreen screen(M5.Display);   // まだ何も確保していない

void drawScene(LGFXVirtualCanvas& g) {
  g.fillScreen(TFT_NAVY);
  g.setTextColor(TFT_WHITE);
  g.drawCentreString("Hello, tiled world!", g.width() / 2, g.height() / 2);
}

void setup() {
  M5.begin();                 // ← ここで画面サイズが確定する
  screen.render(drawScene);   // 初回 render がタイルバッファを確保する
}

void loop() {}
```

素の LovyanGFX でも同じです。`LGFX` パネルを作って渡すだけ：

```cpp
#include <LovyanGFX.hpp>
#include <LGFX_AUTODETECT.hpp>
#include <LGFXVirtualCanvas.h>

static LGFX lcd;
LGFXVirtualScreen screen(lcd);
// setup(): lcd.init();  screen.render(drawScene);
```

### 順番の約束ごと（ここを間違えると動かない）

1. **`LGFXVirtualCanvas.h` は、グラフィックスライブラリより後に include する。**
   ヘッダは LovyanGFX / M5GFX / M5Unified のどれが居るかを見て自分を組み立てます。
2. **コンストラクタでは何も確保されません。** グローバルに置いてよいのはこのためです
   （`M5.begin()` 前は画面サイズが分からないので、確保しようがない）。
3. **確保は `begin()` か初回 `render()` のとき。** どちらも `M5.begin()` / `lcd.init()`
   より**後**で呼ぶ必要があります。

### 3 つの型の役割

| 型 | 何者か |
| --- | --- |
| `LGFXVirtualScreen` | **画面全体**を管理する人。設定・確保・タイルループ・転送を持つ |
| `LGFXVirtualSprite` | **画面の一部の矩形**を管理する人。中身は同じエンジン（[10 章](#10-画面の一部だけ更新する--lgfxvirtualsprite)） |
| `LGFXVirtualCanvas` | **描画面**。あなたの描画関数に渡ってくる `g` がこれ |

`g` は「全画面サイズの Canvas」に見えます。`g.width()` は**タイル幅ではなく面の幅**を返します。
実体は現在のタイル sprite への転送役で、`y -= offsetY` してから本物の描画を呼び、
タイル外はクリップで捨てます（SPEC §6）。

## 6. 描画関数の書き方（View と Model を分ける）

### コールバックは関数ポインタのみ

コードサイズを抑えるため、`std::function` もキャプチャ付きラムダも**渡せません**。

```cpp
int score = 0;
screen.render([&](LGFXVirtualCanvas& g){ ... });   // ✗ コンパイルエラー（キャプチャ有り）
screen.render([](LGFXVirtualCanvas& g){ ... });    // ✓ キャプチャ無しラムダは可
```

### 状態は「引数で」渡す

グローバル変数に逃げる必要はありません。第 2 引数に状態を渡すと、そのまま描画関数へ届きます
（`void*` へのキャストも不要、型はコンパイラが見ています）。

```cpp
struct AppState { int score, playerX, playerY; };
AppState state;

void drawScene(LGFXVirtualCanvas& g, AppState& s) {   // ← 型付きで受け取る
  g.fillScreen(TFT_BLACK);
  g.setCursor(10, 10);
  g.printf("Score %d", s.score);
  g.fillRect(s.playerX, s.playerY, 16, 16, TFT_GREEN);
}

void loop() {
  updateState(state);                 // Model を進めるのはここ（1 フレームに 1 回）
  screen.render(drawScene, state);    // View は「今の状態を描くだけ」
}
```

この形（**View と Model の分離**）を強く勧めます。理由は 3 つあります。

- **描画関数がタイル数ぶん呼ばれても安全**になる（[9 章](#9-最重要の落とし穴コールバックはタイル数ぶん走る)）。
  状態を進める場所が 1 箇所に固定されるからです。
- 同じ描画関数を、直接描画・タイル描画・ホスト上のヘッドレステストで**使い回せます**。
- 分割数を変えても絵が変わらないことを、テストで機械的に検証できます
  （このライブラリ自身がそうしています → [tests/](../tests/)）。

## 7. メモリと分割数の決め方

### 何も指定しないとどうなるか

既定は「**1 タイル ≈ 19 KB に収まるように分割する**」です。分割数を固定するのではなく
**タイルの大きさ**を固定するので、面のサイズに応じて分割数が自動で決まります。

| 面 | 既定で解決される分割 | タイル RAM 合計 |
| --- | --- | --- |
| 64×48 | 1（単一バッファ） | 6 KB |
| 128×96 | 2（ダブル） | 約 24 KB |
| 240×160 | 4（ダブル） | 約 38 KB |
| 320×240 | 8（ダブル） | 約 38 KB |

Core2 のベンチでは、この 1 つの数値が**測定した全サイズで実測最適の分割を再現**しました
（SPEC §10.6）。「とりあえず何も指定しない」が本当に妥当な既定です。

### 自分で指定する（優先順位つき）

```cpp
screen.setMemoryLimit(20 * 1024);   // ① タイルバッファの上限バイト数（主役）
screen.setSplitCount(4);            // ② タイル数を固定
screen.setTileHeight(40);           // ③ タイル高を固定（列分割なら setTileWidth）
```

複数指定したときの優先順位は **① > ② > ③ > 既定（19 KB）**。
どれも「確保前」に呼びます。確保後に変えたら `begin()` で作り直してください。

考える単位は**タイル数より RAM** にするのがおすすめです。分割数は結果であって目的ではありません。

### 失敗したら黙って直さない

これは意図的な設計です。**確保できないとき、ライブラリは勝手に分割を増やしたりタイルを
小さくしたりしません。**「頼んだものが用意できなかった」ことが必ず呼び出し側に届きます。

```cpp
void setup() {
  M5.begin();
  screen.setMemoryLimit(8 * 1024);
  if (!screen.begin()) {                     // 任意：ここで確保して結果を見る
    Serial.println("alloc failed");          // ← 気づける
    M5.Display.drawString("alloc failed", 10, 10);
    return;
  }
  Serial.printf("tiles=%d tileH=%d\n", screen.tileCount(), screen.tileHeight());
}
```

- `begin()` は失敗で `false`。
- 未確保のまま `render()` を呼ぶと、**何も描かずに** `false` を返します（ゴミは出しません）。
- `begin()` を省いても初回 `render()` が確保を試みます（ガードレール）。ただし
  戻り値を見られる `begin()` を書くほうが、原因の切り分けは確実に楽です。

動く例は [examples/MemoryBudget](../examples/MemoryBudget/) にあります。

### auto-clear

各タイルは描画前に背景色（既定 黒）でクリアされます。1 枚のバッファを全タイルで
使い回すので、これが無いと前のタイルの残骸が見えてしまうからです。

```cpp
screen.setBackgroundColor(TFT_NAVY);   // クリア色を変える
screen.setAutoClear(false);            // 上級者向け：毎回 fillScreen するなら二度塗りを省ける
```

> ⚠️ **色は C++ の型で解釈されます**（LovyanGFX 全体の流儀）。
> `int` / `uint16_t`（`TFT_*` 定数、`color565()` の戻り値）は **RGB565**、
> `uint32_t` は **RGB888**。`setBackgroundColor(TFT_NAVY)` と
> `setBackgroundColor((uint32_t)0x000080)` は同じ意味ですが、
> `setBackgroundColor((uint32_t)0x000F)` は navy になりません。

`setAutoClear(false)` にすると、**描かなかった画素は不定**になります。
毎フレーム必ず全面を `fillScreen` するシーンでのみ使ってください。

## 8. 速度の話 — 描画律速と転送律速

ここは直感と逆になる部分なので、実測値と一緒に押さえてください。
1 フレームの時間は、ダブルバッファならおおよそ **max(Σ描画, Σ転送)** です。

- **Σ転送は分割数に依らない。** 面の全画素をちょうど 1 回ずつ送るだけなので、
  面積と SPI クロックだけで決まります。320×240 で約 32 ms。
- **Σ描画は分割数とともに増える。** コールバックがタイルごとに再実行され、
  各プリミティブがタイルごとに走査されるからです（描かれるのはタイル内だけですが、
  「判定する」コストは毎回かかります）。

したがって：

| 状況 | 何が起きるか | どうすべきか |
| --- | --- | --- |
| **転送律速**（Σ描画 < Σ転送） | 描画は転送の裏に隠れる | **分割を増やすと速くなる**（重なりが細かくなる） |
| **描画律速**（Σ描画 > Σ転送） | 転送はもう隠れている。増えるのは冗長描画だけ | **タイルは少なく大きく**。理想は 1 タイル |

### Core2 実測（320×240、`bench/`）

**軽いシーン（転送律速）**

| 方式 | 1 フレーム | fps |
| --- | --- | --- |
| A 直接パネル（バッファ無し・ちらつく） | 36.9 ms | 27.1 |
| C 単一バッファ split=8 | 32.6 ms | 30.7 |
| **D ダブルバッファ split=8（＝既定）** | **31.0 ms** | **32.3** |

転送の床（約 32 ms）にきれいに張り付きます。**直接描画より速い**のは、
タイルを 1 トランザクションにまとめ、DMA と描画を重ねているからです。

**重いシーン（描画律速）**

| 方式 | split=2 | split=8 |
| --- | --- | --- |
| A 直接パネル | 12.2 fps | — |
| C 単一バッファ | 24.9 fps | **18.0 fps**（分割で悪化） |
| D ダブルバッファ | 28.2 fps | 30.1 fps |

単一バッファでは分割を増やすほど遅くなる（冗長描画がそのままフレーム時間に乗る）のに対し、
ダブルバッファはそれを転送と重ねて吸収します。既定が「タイル 2 枚」なのはこのためです。

### 覚えておくと判断が速くなる原則

- **分割数を増やしても Σ描画は減らない。** 増えるのはタイルごとのオーバーヘッドだけ。
  タイルは「RAM を減らすための道具」であって、速くするための道具ではありません
  （ダブルバッファで転送を隠せる範囲でだけ、結果的に速くなります）。
- **転送時間は面積と SPI クロックだけで決まる。** 描画の最適化では下がりません。
  下げたいなら、送る面積を減らす（[10 章](#10-画面の一部だけ更新する--lgfxvirtualsprite)）か、
  送る回数を減らす（[11 章](#11-差分転送--変わっていないタイルを送らない)）。
- **描画が重すぎるときは、分割を減らす。** `setMemoryLimit()` を大きく、
  あるいは `setSplitCount(1)`。ライブラリは律速を自動判定しません
  （コールバックの中身は事前に分からないため。SPEC §10.6）。

## 9. 最重要の落とし穴：コールバックはタイル数ぶん走る

**1 フレームで、あなたの描画関数はタイル数だけ呼ばれます。** 320×240 の既定なら 8 回です。
絵は正しく出ます（タイル外はクリップされる）。壊れるのは**副作用と、クリップで減らない処理**です。

### やってはいけないこと

```cpp
// ✗ ダメな例
void bad(LGFXVirtualCanvas& g) {
  int v = analogRead(36);          // タイルごとに読む → 8 個の違う値で帯ごとに絵が食い違う
  int t = millis();                // 同上。アニメがタイル境界でずれる
  g.drawPng(logo, sizeof(logo), 0, 0);  // PNG を 8 回フルデコードする
  g.fillRect(0, 0, v, 10, TFT_RED);
}
```

### 正しい形

```cpp
// ✓ 状態は loop() で進め、描画関数は「読むだけ」
struct App { int level; uint32_t t; };
App app;

void good(LGFXVirtualCanvas& g, App& s) {
  g.fillScreen(TFT_BLACK);
  g.fillRect(0, 0, s.level, 10, TFT_RED);
  g.pushImage(0, 20, LOGO_W, LOGO_H, logo565);  // RAM 上の生画素なら安い（下記）
}

void loop() {
  app.level = analogRead(36);      // 1 フレームに 1 回
  app.t     = millis();
  screen.render(good, app);
}
```

### 「クリップで減る処理」と「減らない処理」

これが分かれ目です。

| 処理 | タイル分割すると |
| --- | --- |
| `fillRect` / `drawString` / `fillCircle` など | **クリップされる**（タイル内の画素しか塗らない）。増えるのは判定コストだけ |
| **RAM 上の**画素からの `pushImage` | **クリップされる**（そのタイルぶんの行しか読まない）。安い |
| `drawPng` / `drawJpg` / `drawBmp` | **減らない。** 1 行出すにも圧縮ストリーム全体を処理するため、**毎タイル フルデコード** |
| SD / フラッシュからのファイル読み込み | **減らない。** 毎タイル 再オープン・再読み込み |
| PSRAM 上のソース画像のサンプリング | **減らない。** 遅いメモリを毎タイル読み直す |
| 大きな LUT の構築、レイアウト計算、センサポーリング、通信 | **減らない。** そのまま N 倍 |

**対策は 1 つ、「一度だけやって、あとは blit」。**

```cpp
static M5Canvas logo(&M5.Display);      // 内蔵 RAM 上に持つ

void setup() {
  M5.begin();
  logo.createSprite(LOGO_W, LOGO_H);
  logo.drawPng(logoPng, sizeof(logoPng), 0, 0);   // ← デコードはここで 1 回だけ
}

void drawScene(LGFXVirtualCanvas& g) {
  g.pushImage(10, 10, LOGO_W, LOGO_H, (uint16_t*)logo.getBuffer());  // 毎タイル、でも安い
}
```

これで **N 回のデコード**が **1 回のデコード + N 回のクリップ済み blit** になります。
どうしても重い処理をコールバックに置くしかないなら、**タイルを少なく大きく**して
N を下げてください（`setMemoryLimit` を大きく／`setSplitCount` を小さく）。SPEC §10.7 参照。

## 10. 画面の一部だけ更新する — `LGFXVirtualSprite`

「画面の大半は固定で、一部だけ動く」なら、全画面を送る必要はありません。
`LGFXVirtualSprite` は**任意の矩形サブ領域**を、同じタイル分割エンジンで管理します。

```cpp
LGFXVirtualSprite view(M5.Display, 200, 150, 20, 60);  // (20,60) に置く 200×150

void drawView(LGFXVirtualCanvas& g, Ball& b) {   // ← 座標はスプライトの「ローカル」
  g.fillScreen(TFT_BLACK);                       //    (0,0) = 領域の左上
  g.drawRect(0, 0, g.width(), g.height(), TFT_DARKGREY);  // width() は 200 を返す
  g.fillCircle(b.x, b.y, 10, TFT_CYAN);
}

void setup() {
  M5.begin();
  M5.Display.fillScreen(TFT_NAVY);
  M5.Display.drawString("Static title", 20, 20);  // 領域の外。以後 誰も触らない
  view.setMemoryLimit(12 * 1024);
  view.begin();
}

void loop() {
  update(ball);
  view.render(drawView, ball);       // 200×150 だけを更新（＝転送量が 1/2.5）
  delay(16);
}
```

- 設定 API（`setMemoryLimit` / `setSplitCount` / 差分 / 透過 …）は `LGFXVirtualScreen` と同じです。
- `setPosition(x, y)` で移動できます（**再確保なし**）。`render(draw, x, y)` は
  「そこへ描いて、現在位置も更新」。動くアイコンやカーソルに向きます。
- 領域が画面からはみ出しても安全です（パネル側のクリップが吸収します）。

`LGFXVirtualScreen` は「面＝画面全体」という特殊ケースにすぎず、両者は同じエンジンです。
動く例は [examples/Viewport](../examples/Viewport/)。

> **注意：** スプライトが触らない画素は**誰も描き直しません**。上の例の
> 「Static title」は最初の 1 回だけ描いています。裏に何かが変化する設計にするなら、
> 変化したときに自分で描き直す責任はアプリ側にあります。

## 11. 差分転送 — 変わっていないタイルを送らない

前フレームと同じ内容のタイルは、送らなくても画面は同じままです。
`setDiffMode(LGFXVirtualDiffMode::Tile)` でそれを有効にできます（**既定は OFF**）。

```cpp
screen.setDiffMode(LGFXVirtualDiffMode::Tile);
screen.begin();

// …描いた後
Serial.printf("%u / %u px 転送\n",
              (unsigned)screen.diffPushedPixels(),
              (unsigned)screen.diffTotalPixels());
```

各タイルは描画後にハッシュ（1 タイル 8 バイト）を取り、前回と一致したら転送を飛ばします。
**出力画素は 1 ピクセルも変わりません** — 転送だけの最適化です。

**得をする場面は限られます。**

- 減るのは**転送だけ**。描画コールバックは従来どおり全タイルで走り、
  さらにハッシュ計算（タイルバッファ 1 回の線形走査）が**増えます**。
- したがって **大きくて転送が遅いパネル**（フル HD の USB ディスプレイなど）向けです。
  Core2 の 320×240 のような小さく速いパネルでは、転送画素は減ってもフレーム時間は
  ほとんど変わりません。既定 OFF なのはこのためです。効いているかは必ず実測してください。
- 粒度は**タイル単位のみ**。タイル高はメモリ予算で決まるので、大きなパネルでは自動的に
  細かくなります（フル HD・既定予算ならタイル高 5 行＝画面の 1/216）。

> ⚠️ **他が画面に触ったら `invalidate()` を呼ぶ。** 転送を省略できるのは
> 「送らなかった場所にはまだ前回の絵が残っている」前提が成り立つ間だけです。
> 再確保・設定変更・スプライトの移動・パネルの回転/サイズ/色深度の変化は自動で検知しますが、
> それ以外は検知できません。**`lcd.fillRect()` で直接描いた／別の面を重ねた／
> パネルをスリープ・リセットした／USB ディスプレイが再接続した** ── こうしたときは
> `screen.invalidate()` を呼んでください（次の `render()` が全タイルを転送します）。

動く例は [examples/DiffTransfer](../examples/DiffTransfer/)。SPEC §21 も参照。

## 12. 透過オーバーレイ（ダイアログ）

「動作中の画面の上に確認ダイアログを出したい。でも下の画面は描き直したくない
（重いし、一瞬消える）」。これが `renderTransparent()` です。

しくみは単純です。タイルを**透過色**でクリアし、その色**以外**の画素だけをパネルへ送ります。
透過色のままの画素は転送されないので、パネルの内容がそのまま残ります。
だから**角丸ダイアログの角から下の画面が見えます**。

```cpp
LGFXVirtualScreen background(M5.Display);
LGFXVirtualSprite  dialog(M5.Display, 200, 110);   // ダイアログの外接矩形

void drawDialog(LGFXVirtualCanvas& g) {   // fillScreen しない：描かない部分が透ける
  g.fillRoundRect(0, 0, g.width() - 6, g.height() - 6, 10, TFT_DARKGREY);
  g.drawRoundRect(0, 0, g.width() - 6, g.height() - 6, 10, TFT_WHITE);
  g.drawString("Delete everything?", 14, 18);
}

void loop() {
  M5.update();
  if (M5.BtnA.wasPressed()) dialog.renderTransparent(drawDialog);  // 下はそのまま
  if (M5.BtnB.wasPressed()) background.render(drawBackground, state);  // 閉じる＝下を描き直す
}
```

**知っておくべきこと。**

1. **閉じるときは、下の画面を自分で描き直す。** ライブラリはレイヤを管理しません。
   ダイアログが触っていない画素は誰も復元できないので、それはアプリの責任です。
2. **矩形のダイアログなら透過は要りません。** その位置に置いた `LGFXVirtualSprite` が
   すでに「その矩形だけ」を送っており、そのほうが速い。
   **形のあるダイアログの最良手は両方の組み合わせ**：外接矩形にスプライトを置き、
   それを透過 push する（上のコードがそれです）。
3. **アルファブレンド（半透明）はできません。** マスクは画素単位のオール・オア・ナッシングです。
   真の合成には全画面バッファかパネル読み戻しが要ります。
4. **コストの性質が違う。** マスク付き転送は 1 走査線ずつ処理し、見える画素の run ごとに
   ウィンドウ設定を発行するので、**画素あたりでは通常の `render()` より遅い**。
   得をするのは送る画素数が激減するからです（全透過の走査線は転送ゼロ）。
   描画コールバックは全タイルで走ることに変わりはありません。
5. 差分転送と併用するなら規則が 1 つ増えます：**オーバーレイの下を何かが描き直したら
   `overlay.invalidate()`**。

透過色の既定は `TFT_TRANSPARENT`（RGB565 `0x0120`）。絵が本当にその色を使う場合だけ変更します。

```cpp
dialog.setTransparentColor(M5.Display.color565(1, 2, 3));
```

> ⚠️ ここも[色の型の話](#auto-clear)が効きます。`setTransparentColor(TFT_TRANSPARENT)` と
> `setTransparentColor((uint32_t)0x002400)` は同じ色ですが、
> `setTransparentColor((uint32_t)0x0120)` は**違う色**です。

`render(...)` の各形には、同じ引数の `renderTransparent(...)` が存在します。
通常の `render()` の挙動は一切変わりません。
動く例は [examples/Dialog](../examples/Dialog/)。SPEC §22 も参照。

## 13. 列分割と PSRAM

どちらも「普通は要らないが、要る場面でははっきり要る」設定です。

### 列分割

既定は横帯を上から下へ。`Columns` にすると**面いっぱいの高さの縦帯**を左から右へ送ります。
長尺印刷・ティッカー・横長波形など、**左から右へ送り出したい対象**向けです。

```cpp
screen.setSplitAxis(LGFXVirtualSplitAxis::Columns);
screen.setTileWidth(32);   // 任意（列分割での setTileHeight 相当）
```

描画コールバックは**何も変えなくて構いません**。出力画像も行分割と完全に同一です
（parity テストが全分割数でピクセル一致を検証しています）。

**唯一の例外がテキストの折り返し**です。LovyanGFX はタイル sprite 自身の右端で折り返すため、
列分割ではタイル境界で折り返してしまい、出力が分割数に依存してしまいます。
そこで**列分割では X 方向の折り返しを強制的に無効化**し、長い行はクリップします。
改行は面の左端に戻すよう補正済みなので、`println` / `printf` は期待どおり動きます。

### PSRAM 上のタイルバッファ

大きなパネルでは、内蔵 RAM 既定だとタイル数が非常に多くなり、その全部でコールバックが
再実行されます（フル HD なら 200 タイル超）。`setUsePsram(true)` は
「遅いメモリと引き換えに、少なく大きいタイル」を選ぶための逃げ道です。

```cpp
screen.setUsePsram(true);
screen.setMemoryLimit(2 * 1024 * 1024);
screen.begin();
if (!screen.tileIsPsram()) Serial.println("内蔵 RAM に確保された");
```

- **無条件に速くはなりません。** PSRAM は描くのも読むのも遅く、しかも
  **LovyanGFX は PSRAM 上の sprite を DMA 無しで push**します。重ねる相手が無くなるので、
  auto のダブルバッファは **OFF に解決されます**。
  コールバックが律速なら勝ち、転送が律速なら負け。実測してください。
- **ここだけはフォールバックします。** PSRAM が無い/足りなければ内蔵 RAM に確保され、
  描画は成功します（分割数やサイズは変わらず、変わるのは速度だけなので）。
  実際どちらに置かれたかは `tileIsPsram()`、要求したかどうかは `usePsram()`。

両方の動く例が [examples/ColumnSplit](../examples/ColumnSplit/) にあります。

## 14. LovyanGFX / M5GFX のクセ

`LGFXVirtualCanvas` は LovyanGFX の API をそのまま映しているので、素の API のクセも
そのまま出ます。つまずきやすい点を挙げます。

### 描画状態はスティッキー（一番の罠）

`setTextColor` / `setTextDatum` / `setTextSize` / `setFont` は**設定したら残ります**。

```cpp
g.setTextDatum(middle_center);
g.drawString("A", 100, 60);
g.drawString("B", 100, 90);   // ← こちらも middle_center のまま
```

**タイル分割ではこれが特に効いてきます。** タイルごとに新しい `LGFXVirtualCanvas` が
渡されるので、「前のタイルで設定したはず」は成立しません。
**描画関数の中で、必要な状態は毎回自分で設定してください。**
「今こうなっているはず」を前提にしない ── これが分割数に依らない絵を作る規律です。

### 色は 24bit で書けるが 16bit に丸められる

`0x4CAF50` のような指定は受け付けられますが、内部で RGB565 に量子化されます。
**「別の色のつもりが同じ色になる」**ことが起きえます（透過色との衝突に注意）。
加えて、[7 章](#auto-clear)の「型で解釈が変わる」問題があります。

### フォントは Flash を食う。CJK は桁違いに食う

プリセットフォントはバイナリに焼き込まれます。ラテン系は数 KB〜数十 KB ですが、
**日本語・中国語・韓国語のフォントは数百 KB〜MB 級**です。

### `startWrite` / `endWrite` は自分で呼ばない

タイル描画中は `LGFXVirtualScreen` / `LGFXVirtualSprite` がトランザクションと DMA 順序を
管理しています。だから描画関数に渡る Canvas には**これらを公開していません**
（呼ぼうとするとコンパイルエラー）。ライブラリはタイルループ全体を 1 回の
`startWrite()` / `endWrite()` で囲み、N 回の転送を 1 トランザクションに束ねています。

### アンチエイリアスとタイル境界

`drawSmoothLine` / `fillSmoothCircle` などの**近傍参照を伴う描画**は、
タイル境界で全画面描画と完全一致しないことがあります（各タイルが独立に描画・クリップされるため）。
LovyanGFX の既定プリミティブは AA 無しなので、通常は問題になりません。

## 15. 使えない API と、その理由

`LGFXVirtualCanvas` は「タイル化された仮想面から安全に提供できる API」を一通りラップしています
（図形・テキスト・画像・色・状態・現在タイルからの読み戻し）。
**ラップしていないメソッドの呼び出しはコンパイルエラーになります。**
黙って間違った絵を出すより、はっきり止まるほうが良いという設計判断です。

外してあるのは次の 4 系統です。理由も知っておくと、代替を自分で選べます。

| 外してある API | なぜ |
| --- | --- |
| `writeColor`, `pushPixels`, `pushBlock`, `writePixels`, `pushColors` … | 呼び出し側が管理する write window / ストリームカーソルに依存し、タイル単位で安全にクリップするための仮想座標情報が足りない |
| `setWindow`, `startWrite`, `endWrite`, `beginTransaction`, `initDMA`, `waitDMA` | タイル描画中は管理側が握っている。公開するとクリップや DMA 順序の保証を壊せる |
| `scroll`, `copyRect` などスクロール／コピー系 | 面内で既存ピクセルを移動する API だが、1 つのタイルには面の一部の帯しか存在しない。タイルをまたぐ元ピクセルを参照できない |
| `pushSprite`, `pushRotated`, `pushAffine` …／`pushImageAffine` 系／`createPng` | `pushSprite` 系は「sprite 自身を別の面へ転送する」もので、Canvas は既に描画先。affine は行列に転送先座標が埋まっており単純なオフセット補正では成立しない |

**代わりに何を使うか。**

- 画素をまとめて置きたい → `pushImage`（タイルごとに正しくクリップされます）
- 領域だけ更新したい → `LGFXVirtualSprite`（[10 章](#10-画面の一部だけ更新する--lgfxvirtualsprite)）
- スクロール表示がしたい → 状態（オフセット値）を自分で持ち、**毎フレーム描き直す**

全対応表は [README.ja.md](../README.ja.md#api) と SPEC の付録にあります。

## 16. 利点と限界

### 向いていること

- **ちらつきを、全画面バッファ無しで消せる。** 320×240 なら約 38 KB。
  しかも小さな確保に分かれるので、断片化したヒープでも通ります。
- **描画コードが分割を知らなくていい。** 全画面座標で 1 つ書けば、1 タイルでも 8 タイルでも
  同じ絵になります（ヘッドレステストがピクセル一致を検証しています）。
- **既定のまま実測最適に近い。** タイル予算・ダブルバッファ判定は面サイズから自動で決まります。
- **速い。** Core2 では直接描画（27fps・ちらつきあり）より速く、SPI の床（約 31fps）に乗ります。
- **部分更新も透過オーバーレイも同じエンジンで扱える。**
- **同じ描画関数をホスト上でテストできる。**

### 向いていないこと（設計上の非目標）

- **GUI フレームワークではありません。** ボタン・タッチ・フォーカス・イベントは
  一切ありません。入力処理はアプリ側です。それが要るなら LVGL を検討してください。
- **レイアウトエンジンではありません。** 座標は自分で決めます。
  （レイアウトを外に出したいなら [LGFXScreenBuilder](https://github.com/tanakamasayuki/LGFXScreenBuilder) が
  この上に乗ります。）
- **リテインドモードではありません。** 描画命令を記録しないので、毎フレーム全部描き直します。
  差分転送（既定 OFF）が減らすのは**転送だけ**で、描画は減りません。
- **2 次元グリッド分割はありません。** 行または列の 1 次元のみ。
- **キャプチャ付きラムダは使えません。**
- **半透明合成はできません。** 透過はオール・オア・ナッシングのマスクです。
- **タイル境界を跨ぐ近傍依存描画**（AA・ぼかし）は全面描画と一致しない場合があります。
- **画像デコードは安くなりません。** クリップで減らないので、自分で 1 回に減らす必要があります
  （[9 章](#9-最重要の落とし穴コールバックはタイル数ぶん走る)）。

要するに、**「毎フレーム全部描き直す前提で、ちらつきの無い絵を小さな RAM で出す」**
ことに最適化されています。

## 17. 困ったときは

| 症状 | 疑うところ |
| --- | --- |
| 何も表示されない | `begin()` / `render()` の戻り値。`false` なら確保に失敗している（フォールバックしません）。`M5.begin()` / `lcd.init()` より後に呼んでいるか |
| `begin()` が false | `setMemoryLimit()` が 1 行ぶん（幅 × 2 バイト）にも満たない／ヒープ不足。予算を上げるか、断片化を疑う |
| コンパイルエラー：そんなメンバは無い | [15 章](#15-使えない-api-とその理由)の意図的に外した API。代替を選ぶ |
| コンパイルエラー：ラムダが渡せない | コールバックは関数ポインタのみ。キャプチャは使えない。状態は第 2 引数で渡す |
| 帯ごとに絵が食い違う | 描画関数の中で値を読んでいる（`millis()` / `analogRead()` / 乱数）。状態は `loop()` で進めて、描画関数は読むだけに |
| 帯の境界に線が出る／継ぎ目が見える | 描画関数の中でテキスト状態を設定し直しているか（スティッキー）。AA 系プリミティブを使っていないか |
| 遅い（重いシーン） | 描画律速。**分割を減らす**（`setMemoryLimit` を大きく／`setSplitCount` を小さく） |
| 遅い（`drawPng` を使っている） | 毎タイル フルデコードしている。setup で 1 回だけ sprite に展開し、`pushImage` する |
| 直接描画より遅くなった | PSRAM タイルを使っていないか（DMA 無効・ダブルバッファ OFF）。`tileIsPsram()` を確認 |
| 未描画部分にゴミが出る | `setAutoClear(false)` にしている。描かない画素は不定になる |
| 背景色／透過色が指定と違う | 値の C++ 型。`TFT_*` / `int` は RGB565、`uint32_t` は RGB888 |
| 差分転送で古い絵が残る | 他が画面に触った。`invalidate()` を呼ぶ |
| 差分転送しても速くならない | 小さく速いパネルでは想定内。転送律速の大画面向けの機能 |
| ダイアログの下が消える | 閉じたら下の面を自分で `render()` し直す必要がある |
| ダイアログの一部が抜ける | その色が透過色（既定 RGB565 `0x0120`）と一致している |
| 列分割で長い行が折り返さない | 仕様（タイル境界で折り返すと出力が分割数に依存するため無効化）。改行は補正済み |
